# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

`tamga-dotnet` is the official .NET SDK for Tamga (license activation, offline verification, machine management for C#/.NET applications). It is one of the eight hand-written, idiomatic, standalone Tamga SDKs — it reimplements every cryptographic verification primitive natively in C# rather than binding to `tamga-c`'s Rust-backed C ABI, so divergence from the Rust reference implementation in the crypto sections is a real interop bug, not a style choice. The authoritative protocol spec — the source of truth for every field name, endpoint path, and enum value — is the Tamga API protocol specification; read its "Known Server-Side Gaps" section before touching anything.

**Current status: fully implemented and published.** Every section (A–M) is real, tested code — client/transport, license validation/check-in/checkout, machine checkout/management/offline proof, components/processes, entitlements, error model, and CI/release automation. Published on NuGet as `Tamga.Sdk` via Trusted Publishing (OIDC); the exact published version is whatever the newest `v*` git tag says, since MinVer derives it at pack time. Sections E, F, H (`Checkout/LicenseFile.cs`, `Checkout/MachineFile.cs`, `Proof.cs`) have each passed a dedicated `security-reviewer` pass — see "Security-reviewer history" under Critical Dependency Notes below for the specific findings, since they aren't otherwise surfaced anywhere outside commit message bodies.

## GOTCHAS

Pulled from the Tamga API protocol specification's "Known Server-Side Gaps" section, scoped to what actually affects this repo. Do not "fix" any of these by making the SDK behave as if the gap were closed — model the real, current server behavior.

- **Auth IS enforced, and license-key auth is off by default.** The server accepts an `Authorization: License <key>` credential only when the license's policy has `authentication_strategy` set to `LICENSE` or `MIXED`; that column defaults to `'TOKEN'`, and `NONE` behaves like `TOKEN` at this gate. Anything else answers `401 LICENSE_NOT_ALLOWED` before any endpoint logic runs — a configuration precondition, not a retryable failure. `LICENSE_SUSPENDED` and (under a `REVOKE_ACCESS` policy) `LICENSE_EXPIRED` are refused at the same front door. Do not write docs or samples that imply a license key works against a freshly created policy.
- **16 of 24 `ValidationCode` values are reachable.** `Models/ValidationCode.cs` models all 24 with lenient unknown-value decoding. `ENTITLEMENTS_MISSING` and `FINGERPRINT_SCOPE_MISMATCH` are now genuinely emitted — `scope.entitlements` and `scope.fingerprint` are enforced server-side. Still never emitted: `BANNED`, `TOO_MANY_USERS`, `HEARTBEAT_DEAD`, `HEARTBEAT_NOT_STARTED`, `COMPONENTS_SCOPE_MISMATCH`, and `CHECKSUM_SCOPE_MISMATCH`/`VERSION_SCOPE_MISMATCH` (unreachable for a new reason — sending those two scope fields now fails the whole call with `422 SCOPE_NOT_SUPPORTED`, which is why `Scope.Version`/`Scope.Checksum` are `[Obsolete]` + `[JsonIgnore]` — kept, not removed alongside the relationship ids, because their obsolete messages carried no removal notice through any shipped release; 2.1.0 adds the announcement and names the next MAJOR), plus `NOT_FOUND` (the handler returns HTTP 404 directly instead).
- **Every JSON:API error's `status` arrives as a STRING** (`"status": "422"`), because the server serializes it with `status.as_u16().to_string()`. `TamgaJsonOptions.Default` therefore sets `NumberHandling = AllowReadingFromString`, and removing it silently unreachable-ifies the entire typed exception hierarchy: the envelope fails to bind, `TamgaErrorMapper.ToException` is never called, and every API error degrades to a bare `TamgaApiException`. Any new `JsonSerializerOptions` used to read an error body must carry the same flag.
- **Machine/core/memory/disk limits ARE checked at creation time**, through the policy's overage strategy — not only by a later validate. So `POST /machines` can `422` with `MACHINE_LIMIT_EXCEEDED`/`CORE_`/`MEMORY_`/`DISK_LIMIT_EXCEEDED`, and `POST /processes` with `TOO_MANY_PROCESSES`. These map to `TamgaLimitExceededException` subclasses carrying `EquivalentValidationCode`. Because the check honours overage, under `ALLOW_ACCESS`/`ALLOW_1_25X_OVERAGE` the create still succeeds and only validate objects — so `ActivateMachineAsync` must keep BOTH the create-time path and the create→validate→rollback path. Do not delete either.
- **`machine.memory` and `machine.disk` are MEGABYTES**, not bytes, on every model and request builder. A caller passing bytes inflates the license's `machines_memory_count` by 1,048,576× and locks out the next activation.
- **`GET /licenses/{id}/entitlements` ignores `page[after]`** — it unions direct and policy-inherited rows, so the keyset cursor was dropped; `limit` (max 100) is the only bound. `ListEntitlementsAsync` must return `NextCursor = null` unconditionally and `GetCachedEntitlementsAsync` must issue exactly one request. Never reintroduce a cursor loop here. `/machines/{id}/components` is different — its cursor works, and there the cursor is synthesized from the last item's id on a full page, because the server emits no `links` object anywhere (`links: None` on every serializer).
- **Quick-validate silently skips its `last_validated_at` write when the request carries an `Origin` header**, with a byte-identical response either way. `AuthTransport.Cookie` is the only transport this SDK sends `Origin` on, so `QuickValidateAsync` falls back to `POST .../actions/validate` when it is configured.
- **`429 TOO_MANY_REQUESTS` is live and handled.** `Transport.cs` parses and caps `Retry-After`, backs off exponentially with jitter, and auto-retries `GET` plus the seven safe `POST` actions (`validate`, `validate-key`, `check-in`, `check-out`, `ping`, `ping-heartbeat`, `reset-heartbeat`) — creates are deliberately excluded so a retry cannot burn a second seat. `ping-heartbeat`/`reset-heartbeat` must be listed explicitly: neither ends with the `/actions/ping` suffix (that is the *process* route), so leaving them off drops throttled heartbeats, which flips machines to `DEAD` and — on a policy that actually sets `require_heartbeat` (it defaults to `FALSE`) — eventually gets them culled. Retry budget is `TamgaClientOptions.MaxRetries` (default 3). `Errors.cs` deliberately has no typed `429` exception: once the budget is exhausted it surfaces as the catch-all `TamgaApiException`.
- **`x-ratelimit-*` IS set on responses — the old "CORS allowlist only" claim was wrong, and it was wrong in this file.** The rate-limit middleware attaches the headers to the response it returns (`shared/rate_limit/middleware.rs:140-143`), on the request it lets through as well as on the `429` it refuses; the CORS expose list (`router.rs:123-126`) is a second, independent fact about browser clients, not the only place the names occur. **Four** headers, not three: `x-ratelimit-window` is set at `:143`, one line past the `:140-142` range every version of this claim has cited — do not model only the first three. Read them with `TamgaTransport.ReadRateLimitInfo`, which returns a `RateLimitInfo`, deliberately a separate type and accessor from `ResponseHeaders`/`ReadResponseHeaders`: `ResponseHeaders` is a positional record, so widening it would change its primary constructor and `Deconstruct` signature. Two semantics that must not drift: `reset` is an **absolute Unix time in seconds**, not a delay (`now + ttl`, `shared/rate_limit/mod.rs:80` — use `ResetAt`), and **absent is not exhausted** (the middleware returns before setting anything when `state.rate_limiter` is `None`, i.e. whenever the Redis pool could not be built, and skips `OPTIONS` preflight — so a missing `remaining` read as `0` throttles a client against a server that never limits it; check `IsPresent`). This is orthogonal to surviving a `429`, which the transport already handles.
- **`Tamga-Environment` request header is not implemented server-side** (gap #7) — it's a planned EE feature with no code path reading it yet. `Transport.cs` must not send it. This is different from `Tamga-Version`/`Tamga-OTP`, which the server does read.
- **The machine heartbeat window IS policy-driven; the 600s figure is only a fallback** (corrects the old gap #8 claim). `Policy::effective_heartbeat_duration_secs` (`tamga-api/src/features/policies/model.rs:260-265`) returns `policy.heartbeat_duration` when set and `600` only when it is null, and the culler measures against `COALESCE(p.heartbeat_duration, 600)` (`tamga-api/src/workers/machine_jobs.rs:213`). Do NOT write "hardcoded 600s", "fixed 600s", or "not driven by `policy.heartbeat_duration`" anywhere. `HeartbeatScheduler.ServerHeartbeatWindowSeconds` keeps its name for source compatibility but documents itself as the DEFAULT. **The other half has now changed and the docs must change with it:** a policy getter exists (`GetPolicyAsync`/`GetLicensePolicyAsync`), `Policy.EffectiveHeartbeatDurationSeconds` applies the server's own fallback, and `GetHeartbeatIntervalAsync(licenseId)` returns window/3 in one call. So "there is no policy getter here" and "the SDK cannot obtain the window" are both now FALSE — do not reinstate either. What remains true: `HeartbeatScheduler` itself still does not adapt. It takes an interval at construction and keeps it, `DefaultInterval` is still ~1/3 of the 600s fallback, and a caller on a shorter-window policy must pass an interval. Do not turn the scheduler into something that polls the policy; sizing it at construction is the deliberate design. `NextHeartbeatAt - LastHeartbeatAt` on a **read-backed** machine (`MachineFile.VerifyAndDecrypt`, `GetMachineAsync`, `ListMachinesAsync`) still recovers the window too — `null` until the machine has pinged at least once, and a snapshot from issue time in the machine-file case.
- **`next_heartbeat_at`/`heartbeat_status` are policy-accurate on SOME routes only — never write a blanket claim either way.** Both are derived from `Machine::effective_window_secs()`, which reads a `policy_heartbeat_duration` column populated only when the loading query joined `policies` (`tamga-api/src/features/machines/queries.rs`). Joined: `find_by_id` (hence machine `check-out`, `generate-offline-proof` and `GET /machines/{id}`) and `list_page` via `LIST_FROM` (hence `GET /machines`). Not joined: `create`, `ping-heartbeat`, `reset-heartbeat` **and `update`**, whose `RETURNING` lists are `machines`-only (`queries.rs:341-356`). In THIS SDK: `CreateMachineAsync`/`PingHeartbeatAsync`/`ResetHeartbeatAsync`/`UpdateMachineAsync` carry fallback-derived values; `GetMachineAsync`, `ListMachinesAsync` and the machine inside a `.machine` file from `CheckOutMachineAsync` carry the real one. (`GenerateOfflineProofAsync` returns only a signature, so the distinction never reaches a caller there.) "This SDK cannot see the heartbeat window" is FALSE as written.
- **Joined-vs-unjoined and write-vs-read are DIFFERENT axes; do not collapse them.** Write-vs-read answers "can this response say `DEAD`?"; joined-vs-unjoined answers "is `next_heartbeat_at` policy-accurate?". `PATCH /machines/{id}` is the case that separates them and is the counterexample to the write-vs-read rule as usually stated: it is a write, but it touches no heartbeat column (`queries.rs:341-350` sets only name/ip/hostname/platform/cores/memory/disk/metadata/updated_at), so the status is judged against a `last_heartbeat_at` as old as it ever was and **`DEAD` is reachable from it** — while its `next_heartbeat_at` is still on the fallback side. The discriminator for `DEAD` is *which columns the write touched*, never the HTTP verb.
- **The 30s PROCESS heartbeat window really is hardcoded** — `const WINDOW: i64 = 30` and `INTERVAL '30 seconds'` in `tamga-api/src/workers/machine_jobs.rs`, with no `COALESCE` against any policy column. `ProcessHeartbeatScheduler`'s docs are correct as they stand; do not "correct" them by analogy with the machine window above.
- **`DEAD` is unreachable from every route this SDK calls — state the loop rule generally, not as a warning about `DEAD`.** Verified in `tamga-api`: `heartbeat_status_within` (`src/features/machines/model.rs:124-146`) computes `age_secs = now - last_heartbeat_at` and returns `DEAD` only when that exceeds the window, but `ping-heartbeat` (`queries.rs:448-470`) writes `last_heartbeat_at = NOW()` in the same statement it returns, so `age_secs ≈ 0` and the answer is `ALIVE`, or `RESURRECTED` when `last_death_event_sent_at` predates the new ping. `create` omits the column (`NOT_STARTED`), `reset-heartbeat` nulls it (`NOT_STARTED`), and `ValidationCode::HeartbeatDead` has zero construction sites — it exists only as an enum variant and its `as_str()`. The correct rule is **"no `HeartbeatStatus` read off a response ends the ping loop"**; the loop ends on cancellation, disposal, or a raised ping (404). Writing "do not stop on `DEAD`" invites a status check that can only ever be dead code. `HeartbeatScheduler.Dead` is retained as public API — a machine-read method would make it live — but documented as unable to fire; it is deliberately NOT `[Obsolete]`, since the event is not deprecated and this repo builds with `TreatWarningsAsErrors` (an attribute would break consumers who subscribe defensively, and would file it next to the "always null / scheduled for removal" members that genuinely are dead).
- **`DEAD` is still a real server state — do not claim it is impossible in general.** It surfaces on machine *reads*, which join the policy (`queries.rs` `LIST_FROM`/`find_by_id` both `LEFT JOIN policies`). Three such routes now reach a caller here: the machine inside a checked-out `.machine` file (`MachineFile.VerifyAndDecrypt`), `GetMachineAsync`, and `ListMachinesAsync`. So `HeartbeatScheduler.Dead` is no longer purely theoretical API — a caller who polls `GetMachineAsync` can genuinely observe it — but it still cannot fire from the ping loop, because the loop's only source of a `Machine` is `PingHeartbeatAsync`. Keep the `Dead` enum value, the `HeartbeatStatus` field, and the regression tests that mock `DEAD` ping responses.
- **No serializer emits a `relationships` object** — licenses and machines alike return `{ type, id, attributes }` only. `License.ProductId`/`PolicyId`/`UserId`/`EnvironmentId` and `Machine.LicenseId` could therefore never be populated from a response. All five were `[Obsolete]` from 2.0.0 and **removed in 2.1.0**; `PolicyReadTests` asserts by reflection that they stay gone. Do not reintroduce any of them, and do not reintroduce a `data.relationships` read on a response mapper — `relationships` exists on the machine and licence CREATE *request* bodies only (`machines/create_machine.rs:26`, `licenses/create_license.rs:27`, `licenses/create_key.rs:21`). A phantom that always answers `null` is worse than an absent member: it reads as "this licence has no policy" instead of "ask `GET /licenses/{id}/policy`". `CreateMachineRequest.LicenseId`, `Release.ProductId` and `Policy.ProductId` are live and unaffected — same suffix, different things.
- **Fresh policies return non-real enum strings** (gap #9): `overage_strategy: "DENY_ACCESS"` and `heartbeat_resurrection_strategy: "NO_RESURRECTION"` are not real `OverageStrategy`/`HeartbeatResurrectionStrategy` variants — the server silently treats them as `NO_OVERAGE`/`NO_REVIVE`. `Models/Policy.cs`'s custom `JsonConverter`s for both enums must decode these two strings to `NoOverage`/`NoRevive` without throwing, and must **not** invent a fake `DenyAccess`/`NoResurrection` C# member that implies restrictive behavior the server doesn't actually apply.
- **Auto-update: `204` means TWO things and the SDK must never call it "up to date".** `CheckForUpgradeAsync` is implemented. `GET /releases/actions/upgrade` (`upgrade_release.rs:35-105`) answers `204 No Content` both when no newer release matches (`:62-64`) and when one exists but the bearer's license is `Expired` under an `expiration_strategy` that denies it (`:92-100`) — deliberately, because a `403` there would leak "a newer version exists but you can't have it" (the server's own comment, `:88-91`). `UpgradeCheck.UpgradeOffered` is named for that; do not add an `UpToDate`/`IsCurrent` member or write docs that say "already current". A **suspended** license is the one nearby case that is loud (`403`, `:77-81`). Four query params are REQUIRED (`product`, `platform`, `filetype`, `version`) and a missing one is rejected by axum's `Query` extractor as **plain text**, not a JSON:API envelope — which is why `UpgradeCheckRequest` makes all four `required`. `ReleaseAttributes` is the only camelCase resource in the whole API (`productId`), with `created`/`updated` explicitly renamed back — **`ArtifactAttributes` is the second, and it has the same exception** (see the artifact gotcha below). ~~A release-artifact download route exists but is gated behind a permission no role holds, so a download method would `403` for every caller; do not add one.~~ **Retracted 2026-08-21** — `tamga-api` `e6d317b` granted `artifact.download` to `Role::LicenseToken` (`shared/authz/mod.rs:265`) and routed a real handler, so the download is reachable with a licence key and the SDK now implements it.
- **Release artifacts are reachable with a licence key as of `tamga-api` `e6d317b`, and the download answers a `303` you must never follow.** That commit added exactly ONE permission per role, `artifact.download` (`shared/authz/mod.rs:265`), and routed a real handler, retiring the "no role holds it" claim above. **Do not write that it added `artifact.read` too** — `Role::LicenseToken` already held `artifact.read` at `:264` before the commit, so listing artifacts and reading their metadata was never blocked and this SDK could have exposed those two routes at any time. Only the byte fetch was refused, and it was not recoverable by granting a token the permission either, because `effective_permissions` intersects the bearer and token sets and the bearer side comes solely from `role.default_permissions()`. Three traps, all measured. **(1) The redirect.** `download_artifact` answers `303 See Other` to a short-lived presigned storage URL by default. `HttpClientHandler.AllowAutoRedirect` defaults to `true` and `Client.cs:21` builds `new HttpClient { Timeout = … }`, which takes that default — so a `303` gets followed off-origin by the credential-bearing client. The obvious statement of the danger is wrong and was corrected by measurement on net8.0 — both hops, against a control request proving the credentials were present to begin with. `HttpClient` **strips `Authorization` on every automatic redirect, same-origin included** (stricter than `fetch`, which keeps it within an origin — so do NOT carry a sibling SDK's answer over to this one, the runtimes genuinely differ), and **forwards a directly-set `Cookie` header on both hops**, which is exactly how `AuthTransport.Cookie` sets `Tamga-Session`. So the leak is the session credential, not the licence key, and no handler default prevents it. It is not hypothetical that storage can be same-origin either: `s3_endpoint` + `s3_force_path_style` (`config.rs:109,117`) allow exactly that. **And there is a second reason that holds whatever the credentials do:** a JSON:API response is read with `ReadAsStringAsync`, so a followed `303` would pull an entire installer into one `string` and then try to parse it as JSON — an OOM, not a parse error. The SDK therefore sends `?redirect=false` **unconditionally** (`BuildDownloadQuery` seeds the parts list with it before looking at `ttl`), takes `redirectUrl` out of the returned resource, and fetches the bytes on a **separate credential-free `HttpClient`** — never the API one. Do not "simplify" either half. **(2) The casing.** `ArtifactAttributes` is `rename_all = "camelCase"` **and** carries explicit `rename = "created"`/`"updated"` (`artifacts/serializer.rs:20,34-37`), so the wire names are `redirectUrl` but `created`/`updated` — NOT `createdAt`/`updatedAt`. It is the second resource with the `Release` exception, and a uniform camelCase mapping yields two silently-null timestamps. **(3) A `403` on download is not necessarily an auth problem.** Unlike `list_artifacts`/`get_artifact`, which check only `artifact.read`, the download route also runs `releases::service::enforce_release_access` (distribution strategy, suspension, expiry, entitlement), so a CLOSED release's binary is refused to a caller that genuinely holds `artifact.download`. Check the release before the credential. Note the corollary: **listing succeeds where downloading fails**, so never infer downloadability from a successful list. **(4) A bad `ttl` answers `PRESIGN_TTL_INVALID`, not `TTL_INVALID`.** `artifacts/service.rs:33` emits the former; the two checkout routes (`check_out_license.rs:48`, `check_out_machine.rs:50`) emit the latter, and only the latter is in `TamgaErrorMapper`. So a download TTL rejection arrives as a bare `TamgaApiException`, NOT `TtlInvalidException`. Deliberately left unmapped — widening an existing typed exception's meaning is not additive — and pinned by a test that asserts the negative. `GetArtifactDownloadUrlAsync` validates the range client-side anyway, so a correct caller should never reach it. Create/update/delete/upload stay out of scope — those permissions are absent from `Role::LicenseToken` and `ArtifactPolicy` additionally gates them on Admin/Developer/ProductToken/EnvironmentToken.
- **Fingerprint canonicalisation is a shared cross-port rule; the .NET-specific traps are the sort comparer and NFC.** `MachineFingerprint.Compute`/`Canonicalize` implement `lowercase_hex(SHA-256(UTF-8("tamga-fingerprint-v1" <US> join(<US>, sort_bytewise("label=trimmed_value")))))`, identical in all eight SDKs, pinned by `tests/Tamga.Sdk.Tests/Fixtures/Fingerprints/fingerprint.json` (9 vectors, 8 rejections, digests from an independent SHA-256 implementation). **Do NOT add `String.Normalize`.** NFC needs a new dependency in Rust and Go and ICU or hand-rolled tables in C11, so a .NET port that normalises becomes the one SDK that disagrees with the other seven about which machine an input describes — two fingerprints, two seats. Same reasoning bans `string.Trim()`: it trims all Unicode whitespace where the rule trims six ASCII characters. **The sort is the live .NET trap.** `Array.Sort(string[])`/`List<string>.Sort()`/`string.CompareTo` are culture-sensitive: measured, `"Disk=x"` vs `"arch=y"` is `+1` under the current culture and `-1` bytewise. `StringComparer.Ordinal` is a **non**-trap — it cannot diverge from a UTF-8 byte sort for any accepted input, because labels are unique ASCII-printable and `=` is ASCII, so the deciding byte is always below `0x80` and a value's bytes never reach the comparison (tamga-js measured 8 732 016 pairs, zero divergence). Do not write a test asserting that difference; it is green for the wrong reason and the mutation survives. Bytewise-vs-code-point is not a distinction at all — UTF-8 byte order *is* code-point order. The two mutations that bite are sorting on the label alone and sorting case-insensitively. **Rejections must throw, never repair:** stripping a control character or deduplicating a label maps two different inputs onto one seat, which is the entire point. And there is deliberately no hardware-reading helper — what identifies a machine is a product decision.
- **Read fixtures as UTF-8 explicitly, even though .NET makes that the default.** `StreamReader(Stream)` defaults to UTF-8 and .NET Core's `Encoding.Default` is UTF-8 on every platform, so this repo is safe by construction — verified, not assumed. It is still spelled out at the one call site that reads a non-ASCII fixture, because tamga-python shipped the equivalent bug and it failed on `windows-latest` **only**: `Path.read_text()` used the platform locale codec (cp1252), the `é` in `non_ascii_value` decoded as mojibake, and the digest differed. That is one SDK disagreeing with itself across two operating systems — the exact failure the shared spec exists to prevent, by a route the spec does not cover. `MachineFingerprintTests.VectorFile_DecodedAsUtf8_NotThePlatformCodepage` fails with a named cause rather than an unexplained hash mismatch. Note the other eight vectors are pure ASCII, so a suite without the non-ASCII one looks green against a mis-decoding reader and proves nothing. For the same reason every non-ASCII literal in that test file is a `\uXXXX` escape, so no source-file decoder is load-bearing.
- **`UriKind.Absolute` is not a URL guard, and believing it is would be a three-OS bug.** Measured on net8.0: `Uri.TryCreate("/relative/path", UriKind.Absolute, out _)` returns **true** on Unix and yields a `file:` URI; so does `"C:\x\y"`. So validating a server-supplied URL as merely "absolute" admits local-filesystem references and does it differently per platform. `GetArtifactDownloadUrlAsync` requires the scheme to be `http` or `https` explicitly. Plain `http` is deliberately allowed — a self-hosted MinIO on a private network is a real deployment.
- **`GET /v1/health` is reachable and is a differential diagnostic.** It is on the public-route list (`require_auth.rs:52-53`, pinned by the test at `:146-149`) and bypasses host-header validation (`host_auth.rs:22-25`). What blocked it was on this side: `TamgaTransport.BuildUri` prefixes `/v1/accounts/{account_id}` unconditionally. `BuildUnscopedUri`/`SendUnscopedAsync`/`SendUnscopedRawAsync` exist solely for this route — do not route account-scoped calls through them. The body is a plain `{status, version, uptime_secs}` object with `Content-Type: application/json`, **not** a JSON:API document, so it must not go through the envelope decoder. Diagnostic value worth keeping in the docs: every call `403`ing with "The Host header does not match any configured host" while `/v1/health` succeeds means the problem is `TAMGA_ALLOWED_HOSTS`, not the caller's credential.
- **The machine collection is OFFSET-paginated; everything else here is keyset.** `GET /machines` returns `meta.page{number,size,total,totalPages}` (`list_query.rs:459-474`) — note `totalPages` carries an explicit `#[serde(rename)]` while `number`/`size`/`total` do not; it is NOT `total_pages`. That is why `OffsetPage<T>` exists separately from `Page<T>`. Do not merge them and do not synthesize a cursor for machines. Params are `page[number]` (alias `page`), `page[size]` (alias `limit`, clamped 1..100), `sort`, `order`, `filter[q]` (alias `q`), plus `filter[license|owner|group|platform]`. Offset past 100 000 rows answers `400 PAGE_OUT_OF_RANGE`.
- **There is NO exact-match fingerprint filter on `GET /machines`.** `filter[q]` is an ILIKE `%term%` across `m.name`, `m.hostname`, `m.fingerprint` (`machines/queries.rs:220`). `FindMachineByFingerprintAsync` must therefore re-check `Fingerprint` for ordinal equality client-side after the search. Do not "simplify" it into trusting the server's result set, and do not invent a `filter[fingerprint]` param — it does not exist. `filter[license]` DOES exist (`list_machines.rs:20-21`) and is what the scoping below uses.
- **The fingerprint lookup MUST stay license-scoped, and a cross-license conflict MUST re-throw.** `FindMachineByFingerprintAsync` takes a license id and sends `filter[license]`; `ActivateMachineIdempotentAsync` passes `request.LicenseId`. An account-wide search looks harmless and is not: the machine resource carries no `license_id` (same fact behind `Machine.LicenseId` having been removed in 2.1.0), so a caller handed another license's machine cannot detect it, and would heartbeat and check out a machine its license does not own while its own `machines_count` stayed zero. That is seat-sharing across licenses — exactly what the wider uniqueness scopes exist to prevent (`machines/service.rs:47-50`). Nothing is lost by scoping: all three strategies' `EXISTS` checks include the caller's own license rows (`service.rs:52-84` — `UNIQUE_PER_LICENSE` on `license_id = $2`, `UNIQUE_PER_POLICY` joining licenses on `l.policy_id = $2` which the caller's license shares, `UNIQUE_PER_ACCOUNT` covering everything), so a genuine re-activation conflicts and is found under every one of them. An earlier revision of the turn-3 spec said the search had to be account-wide; that was retracted.
- **Idempotent activation must never delete an adopted machine.** `ActivateMachineIdempotentAsync` rolls back only a machine it created itself. Deleting a pre-existing row on an over-limit verdict destroys a seat this activation did not take. Combined with the license scoping above, `MachineActivation.AlreadyActivated` carries the strong meaning: "this license already has this machine".
- **`ListMachinesAsync` without `licenseId` is account-wide.** No machine route applies `require_license_scope` and `Role::LicenseToken` holds `machine.read`, so a license key lists every machine in the account. Keep the parameter optional (an admin caller legitimately wants the whole account) but document what omitting it means; do not let a caller assume the server scopes it.
- **Nothing on the server deletes process rows.** The process reaper is dead code, so unlike machines (culled when `policy.require_heartbeat` is set) a process row is permanent until a client removes it, and the rows count against `policy.max_processes`. `DeleteProcessAsync` and `ProcessHeartbeatScheduler.DeleteOnDispose` are the remedy. `DeleteOnDispose` defaults to `false` and its delete runs on `CancellationToken.None` — the token that stopped the pings is the *signal* to clean up, so reusing it would cancel the cleanup.
- **`policy.check_in_interval` is stored as `daily|weekly|monthly|yearly`**, per the column's own `CHECK` constraint (`migrations/20240101000005_create_products_and_policies.sql:152-155`), NOT `day|week|month|year` as this SDK's docs and tests previously claimed. The old converter matched only the noun forms, so `"weekly"` hit the fall-through and decoded to `Day` — a silent sevenfold understatement. Both spellings decode now; the adverbial form is what gets written. Read it with `check_in_interval_count`: the period is `count × unit`.
- **The `Policy` model must carry all 30 attributes the serializer emits** (`policies/serializer.rs:21-53`). It shipped with 16 and silently dropped 14 — the same defect the license model had. `Policy` doubles as its own attributes bag (`FromResource` grafts on `data.id`) precisely so there is one property list, not two that drift. `max_memory`/`max_disk` go the other way: the columns exist and the validator reads them (`policies/model.rs:187-188`, used at `:302`/`:309`) but `policies/serializer.rs` never projects them (`:45-46`, `:83-84` emit `max_machines`/`max_cores` and stop), so they stay and stay `null`. **They are deliberately NOT `[Obsolete]` and were deliberately not removed in 2.1.0 alongside the relationship ids.** Unlike those, these are ordinary `[JsonPropertyName]` bindings on a type deserialized straight from `attributes`, so they light up with no SDK change the day the serializer projects columns it already has — a member the server has not implemented yet is not a deprecated member, which is the same call already made for `Policy.MaxUsers` and `HeartbeatScheduler.Dead`. The license model already carries all 21 of its own.
- **`GET /policies/{id}` is NOT callable with a license key; `GET /licenses/{id}/policy` is.** `get_policy.rs:17` requires `policy.read` (`policies/policy.rs:14-16`), and `policy.read` is absent from `Role::LicenseToken`'s permission list (`shared/authz/mod.rs:236-261`) — so an embedded client gets `403` unconditionally, and no policy setting changes that. `get_license_policy.rs:17` requires `license.read`, which `LicenseToken` does hold. Expose both, route `GetHeartbeatIntervalAsync` through the license one, and have each method's docs point at the other. Do NOT "simplify" by dropping one.
- **`GET /licenses/{id}`, `GET /policies/{id}` and `GET /licenses/{id}/policy` are NOT scoped to the caller's own license — and neither are the machine writes.** None of the three calls `require_license_scope` (its only call sites are `quick_validate.rs:23`, `check_out_license.rs:156,200`, `validate_license.rs:66`, `validate_key.rs:50`); they check a permission plus the account on the bearer and nothing else. One license key can therefore read every license in the account, `attributes.key` in plaintext included. The same omission covers machines: `Role::LicenseToken` holds `machine.read`, `machine.update` and `machine.delete`, and no machine route applies a license-scope check, so a license key can `PATCH`/`DELETE` any machine in the account. **The SDK cannot fix any of this** — do not try, and do not document these surfaces as scoped. Reported upstream.
- **Component and process REQUESTS are flat; their RESPONSES are JSON:API-enveloped. Never read that asymmetry as symmetric.** The request bodies for `POST /components` and `POST /processes` really are flat — `{machine_id, fingerprint, name, metadata}` at the root (`create_component.rs:13-20`, `create_process.rs:13-19`) — and a port that "normalizes" them fails against the live API. But every response on these routes goes through `components::serializer` / `processes::serializer` and comes back as an ordinary `{"data":{"type":…,"id":…,"attributes":{…}}}` document (`components/serializer.rs:12-28,55-67`; `processes/serializer.rs:12-28,55-65`), with creates answering **201**. This SDK decoded those responses flat for its entire life. Because `TamgaJsonOptions.Default` sets no `UnmappedMemberHandling`, the unknown `data` key was ignored silently and nothing threw: `CreateComponentAsync`, `CreateProcessAsync` and `PingProcessAsync` returned objects with `Guid.Empty` ids and empty strings, and `ListComponentsAsync` returned the right *count* of blank components. Fixed by decoding through `JsonApiDocument<T>` / `JsonApiListDocument<T>` and `Component.FromResource` / `Process.FromResource` (each type doubles as its own attributes bag, like `Policy`). **The four routes still go through `SendRawAsync` rather than `SendJsonApiAsync`** — the two creates must send their flat body as `application/json`, and `SendJsonApiAsync` hardcodes `application/vnd.api+json`. Do not "simplify" that away.
- **What made this survive CI was the fixtures, not the code.** `ComponentProcessTests` stubbed the flat shape in every response fixture, so the tests agreed with the bug. When a decode path is wrong, its fixtures are the first suspect — rebuild them from the server serializer, and run them against the unfixed code to prove they bite before fixing anything.
- **`SynthesizeCursor` refuses an all-zero id, deliberately.** A cursor of `00000000-…-0` sorts before every UUIDv7 row, so feeding it back as `page[after]` returns the same first page and a caller looping until `NextCursor` is null never terminates. No correct decode produces an empty id — but a decode bug can, silently, which is exactly what happened here. Truncating a listing is bad; an infinite loop is worse.

- **Offline files survive a signing-key rotation, and "unknown key" is NOT "forged".** An account keeps every Ed25519 key it has signed with (`account_signing_keys`), and every offline file names the one that signed it in its `kid` claim — parsed since v1 but, until now, never used to select a key. Verifying against a single embedded key therefore collapsed "signed before the last rotation" (authentic, licence probably still valid) into the identical `SignatureVerificationException` a forgery produces, locking out a paying customer and sending support to the wrong place. `SigningKeySet` + `LicenseFile.VerifyWithKeySet`/`MachineFile.VerifyWithKeySet` keep the two apart: a `kid` the set does not hold is `UnknownSigningKeyException` (refresh the set), a `kid` it DOES hold whose signature still fails stays `SignatureVerificationException` (refuse the file). Both derive from `SigningKeySelectionException`. **There is deliberately no "try every key" fallback** — it would verify the same files while destroying the distinction, which is the whole point.
- **`kid` hashes the base64 STRING, never the decoded bytes.** `key_id()` (`shared/crypto/license_file.rs:70-77`) takes `&str` and calls `.as_bytes()`: `kid = lowercase_hex(SHA-256(utf8(public_key_base64))[0..8])` — eight BYTES, sixteen hex characters. Decoding first is the natural assumption and it is wrong, and it fails *silently*: it yields a different but perfectly self-consistent id, so every file reports an unknown signing key while the code looks right. `Crypto/Ed25519.KeyId` implements it; `SigningKeyIdTests` pins the correct answer **and the specific wrong one** (`905f28def18eaac0` vs `630dcd2966c43366`) from vectors this SDK did not generate, plus all twelve server-issued machine-file fixture kids. Asserting only the positive does not catch the trap.
- **Index a key set by the SERVED resource id, not by a locally computed one.** `GET /accounts/{id}/signing-keys` sets `id: k.kid` (`accounts/serializer.rs:103-104,122-123`) from the same value it writes into a file's claim, so that is the authoritative side; the local computation is a cross-check, surfaced as `SigningKeySet.InconsistentKeys` and never used for lookup. Decode through the JSON:API envelope — `id` is a SIBLING of `attributes`. Note `SigningKeyResource`/`SigningKeyListDocument` exist *because* `JsonApiResource<T>.Id` is a `Guid` and a kid is sixteen hex characters, which `Guid` cannot parse; reusing the shared envelope throws on every response the server can send.
- **`e3b0c44298fc1c14` means "this server published no key at all", not "your key set is stale".** Both checkout handlers compute the claim as `key_id(account.ed25519_public_key.as_deref().unwrap_or_default())` (`check_out_license.rs:95-97`, `check_out_machine.rs:127-129`), so an account whose key column was never backfilled signs EVERY file with `SHA-256("")` truncated. No key set can hold it (the empty string is not a key), so it is surfaced as its own `UnpublishedSigningKeyException` — the remedy is server-side and telling the caller to refresh would send them nowhere useful.
- **The key-set path is Ed25519-only for machine files, and that is a server property.** `check_out_machine.rs:86-99` picks the *signing* key by scheme (RSA/ECDSA/Ed25519) while `:127-129` derives the `kid` from the Ed25519 key **unconditionally**, and only Ed25519 keys are ever published (`rotate_ed25519` hardcodes `'ed25519'`). So an RSA/ECDSA machine file's `kid` names a real key that cannot possibly verify it, and a scheme-agnostic kid lookup would report an authentic file as forged — reintroducing the rotation defect in a new place. `MachineFile.VerifyWithKeySet` refuses those schemes up front with `SigningKeyNotApplicableException`; verify them through the scheme-taking overload. Nothing is lost: rotation only ever rotates the Ed25519 key. **Do not trust `Fixtures/MachineFiles/manifest.json` on this point** — its generator called `encode_machine_file` directly and derived each `kid` from that file's own signing key, so it carries four distinct kids where production emits one per account. Those fixtures pin the hash rule correctly and must be used for nothing else.
- **`GET /accounts/{id}/signing-keys` is unreachable with a licence key, with no second route.** It requires `account.read` (`accounts/policy.rs:16-18`) and `Role::LicenseToken` does not hold it (`shared/authz/mod.rs:241-268`), so an embedded client gets `403` unconditionally — unlike the `GetPolicyAsync`/`GetLicensePolicyAsync` pair, there is no permission-compatible alternative. That is not fatal: build the set from keys pinned in the binary with `SigningKeySet.FromPublicKeys`, which needs no network at all. `FromPublicKeys` is strict (a mistyped key throws at startup) while `FromResources` is lenient (one unusable row must not strand an account's whole key history) — the asymmetry is deliberate. **An empty key set is normal**, not an error: `account_signing_keys` is written only by `rotate_ed25519`, so an account that has never rotated has no rows.
- **RFC 9421 HTTP message signing is dead code server-side** (gap #6) — no response is ever signed, `Tamga-Accept-Signature` is parsed but unused. Not currently in this SDK's scope at all; don't add response-signature verification expecting a real signature to show up.

## Testing

- Framework: xUnit. `tests/Tamga.Sdk.Tests/` mirrors `src/Tamga.Sdk/` 1:1 — one `*Tests.cs` per source file, same relative path.
- Coverage gate: **80% line coverage, `ThresholdType=line`, `ThresholdStat=total`**, enforced inline by `coverlet.msbuild` — a coverage drop fails `dotnet test` directly, no separate coverage-check job.
- Local run matching CI's gate:
  ```bash
  dotnet test Tamga.sln -c Release \
    /p:CollectCoverage=true /p:CoverletOutputFormat=cobertura \
    /p:Threshold=80 /p:ThresholdType=line /p:ThresholdStat=total
  ```
- CI matrix is `ubuntu-latest` / `macos-latest` / `windows-latest`. This matters more here than in most repos: `AesGcm` and Ed25519 (via `NSec.Cryptography`/libsodium) are OS-crypto-backend-sensitive (OpenSSL on Linux, CNG on Windows, CommonCrypto on macOS, libsodium's own bundled backend for Ed25519). A crypto test that only runs on the author's laptop is not sufficient signal — every test in `Crypto/`/`Checkout/` must pass identically on all three OSes before merging.
- **Confirming a CI result: wait for the slow job to reach a terminal state, then confirm `gh pr checks` exits 0.** Two things mislead here. (1) **Zero checks is ambiguous** — it reads identically whether a run is queued with no jobs spawned yet or no workflow ever matched the PR. `f297f89` still has no `codecov/patch` check for exactly that reason: it predates the removal of `ci.yml`'s `pull_request: branches: [main]` filter, so a PR based on another `fix/*` branch matched nothing and showed zero checks beside a green-looking `MERGEABLE`. Disambiguate with `gh run list --json headSha,status`. (2) **A partial green is the normal mid-run state, not a result.** `test (windows-latest)` is consistently the slowest job by a wide margin — 45s / 56s / **3m09s** for macos / ubuntu / windows on run `32460173876` — so ubuntu and macos report green, and `codecov/patch` even posts, while Windows is still on its Build step. Reading "three of four green" as done would skip precisely the OS whose crypto backend differs (see the matrix rationale above — Windows/CNG is where the off-curve ECDSA divergence was found). Method that holds up: pin by full 40-char head SHA (`GET /actions/runs?head_sha=…`), poll the slow job itself (`GET /actions/jobs/<job-id>`) until its `status` is `completed`, then confirm `gh pr checks <n>` exits 0. `gh pr checks` and `GET /commits/{sha}/check-runs` lag each other by seconds, so let the job endpoint be the trigger and `gh pr checks` the confirmation. **A caution about tooling, not about CI:** earlier revisions of this bullet claimed GitHub was serving phantom run ids and contradictory run states. That was wrong, and it is recorded here so nobody hunts a GitHub bug that does not exist. Every fabricated reading — run ids that answered `404` on the next call, and a job `completed_at` of `08:02:56Z` reported while the clock read `07:49:43Z` for a job that genuinely finished at `07:50:28Z` — came from one agent's background-monitor events, never from a foreground `gh` call; foreground reads were internally coherent throughout, tracking the job step-by-step against elapsed time. Verify CI from the same execution context you trust for everything else, and treat a completion timestamp in the future as proof the reading is fabricated rather than as evidence about CI.
- No live-network HTTP calls in tests — use a mocked `HttpMessageHandler` (`tests/Tamga.Sdk.Tests/Support/MockHttpMessageHandler.cs`).
- **Offline-file format coverage must come from server-issued fixtures, not self-generated ones.** `tests/Tamga.Sdk.Tests/Fixtures/MachineFiles/` holds `.machine` files produced by `tamga-api`'s own `encode_machine_file`, plus a `manifest.json` that `Checkout/MachineFileFixtureTests.cs` iterates — the theory is manifest-driven, so a later fixture drop needs no test edit. Do NOT add a locally-generated `.machine` file there, and do not "simplify" those tests by building the input in C#. A round-trip test that writes and then reads the same file proves only self-consistency: that is exactly how a fleet-wide misreading of `enc`'s layout and the `alg` grammar stayed green in CI for two years while no SDK could open a file the server actually emitted. `Checkout/MachineFileTests.cs` still builds files locally, deliberately — it covers TTL validation, PEM hardening and scheme refusal — but the fixtures are the authority whenever the two disagree, and its locally-built shapes must be kept in step with them (`+v2` alg, signed `meta`, dot-separated encrypted `enc`).
- Sections **E, F, H** (`Checkout/LicenseFile.cs`, `Checkout/MachineFile.cs`, `Proof.cs`) additionally require a mandatory `security-reviewer` pass before merge — this is a CRITICAL-severity gate per the org's code-review rule, not optional per reviewer discretion. A subtle bug in these three files (base64-string-vs-decoded-bytes confusion, wrong verifier picked for a scheme, non-deterministic field ordering breaking a signature check, a key derivation that silently isn't the one the server used) is a silent license-verification bypass, not just a functional bug.

## Critical Dependency Notes

**Cryptography backend — `NSec.Cryptography` is the one non-BCL exception.** `System.Security.Cryptography` only gets native Ed25519 support in **.NET 9+**. Since v0.1 targets `net8.0` exclusively, `Crypto/Ed25519.cs` must use **`NSec.Cryptography`** (a libsodium binding) as a NuGet dependency — this is used both for the license-checkout signature verify (always Ed25519, independent of the license's `scheme`) and the Ed25519 branch of the machine-checkout multi-algorithm verify. Every other crypto primitive in this SDK — RSA (PKCS1v15 + PSS), ECDSA P-256, AES-256-GCM, HKDF-SHA256 — uses BCL `System.Security.Cryptography` types that have been available since **.NET Core 3.0**, so those four need no third-party package. **Do not "simplify" by reaching for a BCL Ed25519 type on net8.0** — it does not exist yet and the build will not compile against it. When the SDK eventually raises its floor to `net9.0`, `Crypto/Ed25519.cs` becomes a candidate for migrating off `NSec.Cryptography` to BCL-native — that migration is explicitly out of scope for v0.1.

**`netstandard2.0` is backlog, not v0.1 scope.** Adding it (for broader compatibility — older Unity/Xamarin consumers) would require a second crypto backend: neither BCL-native `AesGcm` nor any Ed25519 primitive exists on `netstandard2.0`, so it would need a BouncyCastle (or similar) fallback for both, maintained and security-reviewed independently of the net8.0 path. Not worth blocking v0.1 on. Do not silently multi-target `Tamga.Sdk.csproj` without adding that fallback first.

**Versioning & Release.** No `<Version>` in `Tamga.Sdk.csproj` to hand-bump — **MinVer** derives the actual NuGet package version from the git tag at `dotnet pack` time. **release-please** (`release-type: simple`) owns changelog generation and tag creation from conventional-commit messages on `main`; it does not touch a version file (there isn't one for it to edit). These two tools have non-overlapping jobs — don't add a manual version bump step "to be safe."

**Publishing method — NuGet.org Trusted Publishing (OIDC), not a stored `NUGET_API_KEY` secret. Live and verified.** `.github/workflows/release.yml`'s `publish` job requests a GitHub OIDC token (`permissions: id-token: write`, plus `contents: read` — a job-level `permissions:` block replaces rather than extends the workflow-level default, so both must be listed explicitly) and exchanges it for a short-lived (~1 hour) NuGet.org API key via the `NuGet/login@v1` action, validated against a trusted-publishing policy registered at nuget.org under the `Tamga` organization (Package Owner: `Tamga`, Repository Owner: `tamga-sh`, Repository: `tamga-dotnet`, Workflow File: `release.yml`, Environment: none). No long-lived secret is stored in this repo. This supersedes an earlier decision to default to a stored `NUGET_API_KEY` secret — that path was dropped once NuGet.org's Trusted Publishing was confirmed to be a documented, supported flow for `dotnet nuget push` specifically (see the official Microsoft Learn "Trusted Publishing" doc), and because NuGet.org started limiting newly-created API keys to 30 days from 2026-08-17 onward anyway, making a stored long-lived key impractical.

**`NuGet/login@v1`'s `user:` input is the trust policy's *creator* account, not the Package Owner.** It must be set to `necipsunmaz` (the nuget.org login that created the policy), never `Tamga` (the org selected as Package Owner inside that policy) — using the org name there fails the OIDC token exchange with HTTP 401 `No matching trust policy owned by user 'Tamga' was found`, confirmed by a real failed publish attempt (`v1.0.2`) before the fix. `v1.0.3` published successfully on the corrected value — see `tamga.sdk`'s NuGet.org listing.

**Trigger structure — publish is gated on `release-please`'s own job output within the same run, not a separate `on: release: types: [published]` trigger.** `release-please-action` creates the GitHub Release using this workflow's own `GITHUB_TOKEN`, and GitHub Actions never lets a `GITHUB_TOKEN`-authored event trigger another workflow run (loop prevention) — a `release: published` trigger here is structurally unreachable, confirmed empirically (the `v1.0.0` release-PR merge produced a Release but no `release`-event run ever fired). Fixed per `release-please-action`'s own documented pattern: `release-please` job exposes `outputs.release_created` from `steps.release.outputs.release_created`, and `publish` job is gated via `needs: release-please` + `if: needs.release-please.outputs.release_created == 'true'`, all within the same `push`-triggered run.

**Private repo checkout requires `.gitattributes`.** `windows-latest` runners default to `core.autocrlf=true`, converting LF-committed files to CRLF on checkout; with no `.gitattributes` to override that, `dotnet format --verify-no-changes` failed its `ENDOFLINE` rule on Windows only even though repo content was all-LF. Fixed with a repo-root `* text=auto eol=lf`.

**Codecov points at coverlet.msbuild's real output path, not a VSTest collector path.** The coverage-gate step uses coverlet.msbuild (`/p:CollectCoverage=true`), which writes `coverage.cobertura.xml` next to the test project (`./tests/Tamga.Sdk.Tests/coverage.cobertura.xml`) — not into a `./coverage/` directory. An earlier `--collect:"XPlat Code Coverage" --results-directory ./coverage` was a second, unused VSTest collector pointing codecov at an effectively empty directory ("Found 0 coverage files to report" on every run); removed, and `ci.yml`'s codecov step now uses `files:` with the real path directly. **`CODECOV_TOKEN` now reaches this repo's runs, and `codecov/patch` is load-bearing — do not skip it.** An earlier version of this note recorded the token as never having reached a workflow run (`Token required - not valid tokenless upload`); that was true when written and is now false. `ci.yml`'s codecov step passes `slug: tamga-sh/tamga-dotnet` alongside the token, which is required when `CODECOV_TOKEN` is the org's shared Global Upload Token rather than a per-repo one — without it Codecov cannot tell which repo an upload belongs to. `codecov/patch` now posts a real verdict on every PR head, and it fails: `c652acd` **failed at `64.00% of diff hit` (target `83.44%`)**, `8308fcd` passed at `90.40%`, `de9bbfe` at `90.47%`. **Treat a `codecov/patch` failure as a finding, not noise.** That 64% reading is the whole reason the machine-file v2 verification path (alg parsing, the dot-separated `enc` split, `exp` enforcement) got tested at all; writing those tests is what made `test (windows-latest)` fail on `8308fcd`; and that failure is how the Windows/CNG `PlatformNotSupportedException` escaping `MachineFile.VerifyAndDecrypt` on an off-curve P-256 point was found and fixed (`de9bbfe`). A signature-verification divergence on one of three target platforms sat two steps downstream of a patch-coverage number nobody was obliged to look at.

**Security-reviewer history (back-filled from commit messages — not previously surfaced here).** Sections E/F/H have each undergone an independent `security-reviewer` pass: commit `8fa11a5` — PASS after fixing 1 HIGH finding (`PemEnvelope.Strip` threw an untyped exception on crafted overlapping PEM markers instead of a typed parse error); commit `d13ca72` — PASS on the offline-proof path (Section H) after fixing 1 CRITICAL finding (a JSON-field-ordering deviation from the server's alphabetical `BTreeMap`-backed serialization). Both fixes are live in the current code; this note exists so the review trail is discoverable without archaeology through commit history.

## Branch & Commit Convention

Branches: `feat/*`, `fix/*`, `chore/*`, `refactor/*`, `docs/*`
Commits: [Conventional Commits](https://www.conventionalcommits.org/) (`feat: …`, `fix: …`, etc.) — release-please's changelog/version-bump decision is driven directly by these prefixes on `main`, so an inaccurate type on a squashed PR silently mis-triggers (or skips) a release.
